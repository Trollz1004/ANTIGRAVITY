### The `--status` bug was real, and it mattered more than it looks

The earlier run flagged that `--status` calls 2026-10-04 `FAILED`. Confirmed, and found the mechanism: that packet has `exit_code 0`, 18 gates passed, and upload stage `SKIPPED` because it ran with `--upload off`. The old reader has no category for "rendered fine, publishing deliberately off", so it fell through to `FAILED -- stages: unknown`.

This is not cosmetic. The watchdog's close rule and TRO-7's done-condition both read this output. A false `FAILED` means a healthy chain could never close this issue out.

### What I built

`ops/hermes/newsvideo/status.py` — **the first module back as readable `.py`**, not bytecode. Replaces `daily --status` and keeps the same contract (exit 0 = three consecutive shipped mornings), so it is a drop-in for the watchdog check.

Five states, and only `SHIPPED` counts toward the streak:

| result | meaning |
|---|---|
| `SHIPPED` | published; counts toward the streak |
| `NOT ARMED` | rendered + verified, no YouTube credentials (TRO-3) |
| `LOCAL ONLY` | rendered + verified, `--upload off` by choice |
| `FAILED` | a stage or gate actually failed; names which one |
| `NO RUN` | no packet — the task did not fire |

A real stage or gate failure outranks the publishing state, so a 0-byte or silent render can never be dressed up as `NOT ARMED`. `*` marks mornings Task Scheduler fired rather than a human — the actual evidence this issue asks for.

Same two mornings, old reader vs new:

```
2026-10-08   NOT ARMED*   83.619s 1080x1920, 18 gates passed, rendered and verified; no upload credentials
2026-10-04   LOCAL ONLY   87.704s 1080x1920, 18 gates passed, --upload off; the mp4 stays local
```

Both now correct. The old reader had 10-04 as `FAILED` and, in my first cut, I had 10-08 wrong the other way — `BLOCKED` was being caught as a stage failure before it reached the NOT ARMED branch. Fixed and covered by a test.
