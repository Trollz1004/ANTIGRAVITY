## What the MCP Tasks Extension Specifies (`modelcontextprotocol.io` and `modelcontextprotocol/ext-tasks`)

On `modelcontextprotocol.io` under extensions and in the official `github.com/modelcontextprotocol/ext-tasks` repository, the MCP Tasks extension (`io.modelcontextprotocol/tasks`) defines an asynchronous "call-now, fetch-later" execution model for long-running operations, background queues, and human-in-the-loop workflows that cannot complete inside a single blocking `tools/call` round trip without risking transport timeouts or dropped connections.

Under the extension, task support uses progressive capability negotiation. The server advertises task support during initialization (`capabilities.tasks` in the November 25, 2025 specification revision implemented in `@modelcontextprotocol/sdk` v1.24.0 through v1.32.x, and `capabilities.extensions["io.modelcontextprotocol/tasks"]` in the `modelcontextprotocol/ext-tasks` extension specification), and the client opts in via request metadata (`_meta`). When a task-capable client invokes a long-running tool through `tools/call`, the server creates a durable state machine identified by a server-generated `taskId` and immediately returns a `CreateTaskResult` (`resultType: "task"` or a `task` descriptor) carrying `taskId`, initial status (`working`), time-to-live (`ttl`), timestamps (`createdAt` and `lastUpdatedAt`), and a suggested polling interval (`pollInterval`).

A server-managed task moves through five protocol states: non-terminal `working` (running or queued in the background) and `input_required` (paused waiting for external input or approval), and terminal `completed`, `failed`, and `cancelled`. Clients interact with the task lifecycle through `tasks/get` to poll current status and fetch final output once terminal (in `@modelcontextprotocol/sdk` v1.x, `tasks/result` and `tasks/list` are also exposed alongside `tasks/get`), `tasks/update` to supply input when a task is in `input_required`, and `tasks/cancel` to request cooperative cancellation.

In `@modelcontextprotocol/sdk` v1.x (added in `1.24.0` and patched in `1.32.0` for CVE-2026-111767 cross-session task-store isolation), server-side task execution is available via `McpServer.experimental.tasks.registerToolTask(name, config, { createTask, getTask, getTaskResult })` or on the low-level `Server` class by enabling `capabilities.tasks` with a `TaskStore` implementation. One implementation detail is critical for our servers: when an HTTP MCP endpoint creates a new `McpServer` or `Server` instance on every `POST /mcp` request, an in-memory per-request store loses state between `tools/call` and subsequent `tasks/get` polls, so the task state must be backed by a persistent store shared across requests (such as SQLite or the kitchen ticket folders on disk).
